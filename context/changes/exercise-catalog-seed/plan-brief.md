# Exercise Catalog Seed — Plan Brief

> Full plan: `context/changes/exercise-catalog-seed/plan.md`

## What & Why

Ship GymTrack's predefined exercise catalog: ~40 seeded exercises, each tagged with a
primary muscle group and optional secondary groups, readable by logged-in users. This is
roadmap Foundation F-02 (FR-002). The workout-logging loop (S-01), plans (S-02), substitution
(S-04) and volume balance (S-10) all read from it, and the muscle-group tags directly drive
the last two.

## Starting Point

The backend has only the `User` entity and auth. Schema is generated by Hibernate
(`ddl-auto=update`) with no migration tool. Local databases already hold a Hibernate-created
`users` table; the deployed database (Supabase, via Fly.io) has no tables. `/api/**` is already
authentication-protected, and tests use Testcontainers Postgres.

## Desired End State

Locally and in tests, the app starts, Flyway brings the schema up to date and 40 exercises exist.
An authenticated `GET /api/exercises` lists them (optionally filtered by primary muscle group);
unauthenticated calls get 401. The deployed app is configured so Flyway never runs against
Supabase and behaves exactly as today.

## Key Decisions Made

| Decision | Choice | Why (1 sentence) |
| --- | --- | --- |
| Muscle-group model | Primary + secondary groups (enum, stored as strings) | More accurate tagging for compound lifts, which feeds S-04 and S-10. |
| Secondary-group usage | Filter and substitution use primary only; S-10 decides how to weight secondary | The PRD defines no weighting rule, so none is invented here. |
| Seeding mechanism | Flyway; seed inside a versioned migration | Conventional, auditable, and gives later slices a real migration path. |
| Where Flyway runs | Local and tests only; `fly.toml` `[env]` sets `SPRING_FLYWAY_ENABLED=false` and `SPRING_JPA_HIBERNATE_DDL_AUTO=update` | Owner doesn't want Flyway on Supabase yet; a versioned property switch needs no code branching. |
| Local database adoption | `baseline-on-migrate`, baseline version 1, V1 = current `users` DDL | Adopts the Hibernate-created local DB without recreating anything. |
| Local schema management | `ddl-auto=validate` | Prevents Hibernate and Flyway from diverging. |
| API | `GET /api/exercises` + optional `?muscleGroup=` (primary) | Satisfies FR-002 and gives S-04 its lookup; nothing speculative. |
| Catalog content | ~40 English exercises, 4 per each of 10 groups | Covers the main flow and guarantees substitution alternatives. |
| Identity | UUID id plus unique kebab-case `slug` | Matches `User`; the slug is a stable key for later slices. |

## Scope

**In scope:**
- Flyway adoption (local/tests), V1 baseline of `users`, `fly.toml` production guard
- `exercises` + secondary-groups tables, 40-row seed, `MuscleGroup` enum, entity, repository
- `GET /api/exercises` with optional filter, integration and seed-integrity tests

**Out of scope:**
- Running Flyway on Supabase, deploying
- Custom exercises (S-05), write endpoints, get-by-id, pagination
- Frontend, equipment/movement-pattern fields, secondary-group weighting rules

## Architecture / Approach

New `exercise/` package beside `user/`: enum, read-only entity, repository, DTO, controller.
Schema and data come from `db/migration` SQL (V1 users baseline, V2 catalog + seed). The
existing `/api/**` security rule protects the endpoint with no config change.

## Phases at a Glance

| Phase | What it delivers | Key risk |
| --- | --- | --- |
| 1. Flyway locally + prod guard | Flyway + V1 baseline, `validate`, `fly.toml` overrides | V1 must exactly match what Hibernate expects; Boot 4 starter wiring |
| 2. Catalog schema + seed | V2 migration, enum, entity, repository | Tagging quality |
| 3. Read API + tests | `GET /api/exercises`, filter, integration tests | Invalid filter value must be 400, not 500 |

**Prerequisites:** F-01 (minimal-auth) is done; Podman available for Testcontainers and the local database.
**Estimated effort:** ~2 sessions across 3 phases.

## Open Risks & Assumptions

- If deployed as is, production creates empty catalog tables via Hibernate and the endpoint returns `[]` until Flyway is deliberately enabled there. Enabling later needs no baselining (Supabase has no tables yet); snapshot first.
- `flyway-database-postgresql` and the Boot 4.1.1 Flyway starter name need confirming against the BOM.
- `gen_random_uuid()` assumes PostgreSQL 13+ (local and tests use 16; Supabase is newer).

## Success Criteria (Summary)

- A logged-in user can list the full catalog and filter it by primary muscle group (locally).
- The existing local database and a fresh one both end with the same schema and 40 exercises.
- `fly.toml` keeps Flyway off and Hibernate on `update` for the deployed app; all existing auth tests still pass.
